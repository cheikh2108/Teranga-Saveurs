Teranga Saveurs — déploiement avec Supabase
=============================================

1) Prérequis Supabase
---------------------
- Créer un projet sur https://supabase.com
- SQL Editor : exécuter tout le fichier
    supabase/migrations/20260203130000_teranga_init.sql
- Authentication > Users : « Add user » avec email + mot de passe du restaurateur.
  (En dev vous pouvez désactiver la confirmation d’email pour ce fournisseur.)
- Settings > API : copier « Project URL » et « anon public » dans le fichier .env local :
    VITE_SUPABASE_URL=...
    VITE_SUPABASE_ANON_KEY=...

2) Front (site + admin dans la même SPA)
----------------------------------------
- `npm ci` puis `npm run build`
- Hébergez le dossier `dist/` sur tout hébergeur **statique** : Vercel, Netlify, Cloudflare Pages,
  GitHub Pages, etc.
- Définissez les mêmes variables `VITE_SUPABASE_*` dans l’interface de l’hébergeur (build env).

3) Plus de serveur Node maison
------------------------------
L’API Express a été retirée : lecture / écriture passent par Supabase (Postgres + Storage + Auth).

4) Admin « discret »
--------------------
- Pas de lien public vers l’admin (sauf `VITE_SHOW_ADMIN_NAV=true`).
- Chemin personnalisable au build : `VITE_ADMIN_PATH=/votre-segment-secret`
- Connexion : email + mot de passe du compte Supabase Auth (pas l’ancien ADMIN_PASSWORD).

5) Images
---------
- Uploadées dans le bucket Storage `dish-images` (créé par la migration).
- Les URLs publiques sont enregistrées dans `restaurant_settings` / `dishes`.

6) Sécurité (rappel)
---------------------
- La clé « anon » est publique : la sécurité repose sur les politiques RLS (déjà dans la migration).
- Ne commitez jamais la **service_role** key dans le front.
- Pour aller plus loin : 2FA, magic links, ou rôles métier (table `profiles` + RLS).
